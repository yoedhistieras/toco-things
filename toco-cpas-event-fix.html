Fixing Toco's purchase data in Meta so CPAS can go live

This page has two parts. Part A explains the problem in everyday language. Part B is the full specification for the development team.

Part A

Explained without technical terms

For marketing, management, and anyone who needs to understand the problem without reading code.

In short

The goalTurn on CPAS in Collaboration Center, so brands and sellers can advertise with Toco's catalog without a separate catalog built for each of them.

What blocks itMeta rejects Toco's purchase data. According to Meta, some purchases "never went into a cart".

The causePurchases made in the Toco app are reported to Meta as if they happened on the website.

The fixOne part of Toco's backend: the part that reports purchases to Meta. Nothing else needs to change.

What is actually happening

Think of Meta as an auditor matching two records: who put an item in the cart, and who ended up paying. When the two records don't line up, Meta treats the data as unreliable.

Step 1

Add to cart

A shopper in the app taps "add to cart". The app tells Meta: "someone added to cart, in the app." This part is correct.

Step 2

Pay

The same shopper pays. Toco's server tells Meta: "someone paid, on the website." This is wrong, because the purchase happened in the app.

The result

Meta can't match them

In the app, about 7,000 people add to cart every day and nobody pays. On the website, almost everyone who adds to cart pays right away. Neither makes sense.

To be clearReporting payments from the server (rather than from the website or app screens) is fine and is a common setup. Only the origin label is wrong: purchases made in the app must be labelled "app".

Now vs after the fix

Now

Shopping in the app→recorded as "website"
Shopping on the website→recorded as "website"

Every purchase piles up under "website". Meta can't match them with cart activity in the app, so CPAS is rejected.

After the fix

Shopping in the app→recorded as "app"
Shopping on the website→recorded as "website"

Each purchase connects to the cart activity in the same place. Meta can verify the data and CPAS can be turned on.

What we need from developers

No change needed

  • "Add to cart" reporting from the app and the website
  • Toco reporting checkout and payment from the server
  • No new tracking needed on website or app screens

Needs to change

  • The server code that reports checkout and payment to Meta
  • A pixel setting: restrict it to the toco.id domain

Four things to do, in plain words

  1. The server must know whether each order came from the app or the website.The order system doesn't record this today, so everything is treated as website.
  2. Orders from the app are reported as "app", together with the device's identity.Meta uses the device identity to connect the payment with the cart activity in the app.
  3. Orders from the website are reported with the page address and the shopper's browser details.Today 95% of reports have no page address, so Meta struggles to connect them to ad clicks.
  4. Use the shopper's internet address (IP), not Toco's server address.Right now many reports look like they come from "the same person" because they all carry the server's address.

Once developers are done

Results can be checked the same day with Meta's test tool. The status in Collaboration Center usually changes a few days later, because Meta judges the last few days of data. Once it turns green, the marketing team clicks Finish to turn CPAS on.

Glossary

Terms used in Part B, to make conversations with developers easier.

CPAS
Collaborative Ads. A Meta feature that lets brands or sellers advertise using a marketplace's (Toco's) catalog.
Event
One activity report sent to Meta, for example "view product", "add to cart", "checkout" or "pay" (Purchase).
Pixel / dataset
The "inbox" at Meta that collects all of Toco's events. Toco's is called Toco's Pixel.
Conversions API (CAPI)
A way to send events straight from Toco's server to Meta. Toco uses it for checkout and payment.
Facebook SDK
Meta's code inside the Toco app that sends events from the app.
action_source
The origin label of an event: "app" if it happened in the app, "website" if on the website. This is what's wrong for app orders.
content_ids
The product codes bought. They must match the product codes in Toco's catalog.
fbp / fbc
Browser markers Meta sets on the website, used to connect a shopper with an ad click.
Events Manager
The Meta page that shows every event received, including problems.

Current data flow

AddToCart from the app and the web already sits in the right lane. Only the backend Purchase and InitiateCheckout sender needs to change.

Implementation steps

The principle: capture the shopper's data when the checkout request arrives (while the request from the device or browser is still there), store it with the order, and use it when the event is sent. Purchase is usually sent after payment succeeds, when the shopper's request is long gone.

  1. Store tracking context when checkout is created Add columns to orders or a new table (for example order_tracking_context, one row per order):
    • platform: app_android, app_ios or web
    • client_ip and user_agent from the checkout request
    • Web: fbp, fbc (from cookies), page_url
    • App: anon_id, madid (advertiser ID, empty if the user hasn't allowed it), tracking_enabled (tracking consent status), and device data for extinfo
  2. The app sends device identifiers to the checkout API The backend can't know the device's identity on its own, so the app has to include it in the checkout request (header or body):
    • anon_id from the Facebook SDK (Android: AppEventsLogger.getAnonymousAppDeviceGUID(context), iOS: AppEvents.shared.anonymousID)
    • Advertiser ID (GAID / IDFA) if the user allows it, plus the consent status (iOS: ATT result)
    • App version, OS version, device model, locale and timezone for extinfo
  3. Branch the event builder by platform The Purchase and InitiateCheckout sender reads the context from step 1 and builds an app or web payload. See the pseudocode below and the field specification.
  4. Set event time and ID
    • InitiateCheckout is sent when checkout is created. Purchase is sent when payment succeeds.
    • event_time = when it actually happened (unix seconds), not when it's sent. Meta accepts events up to 7 days old.
    • event_id unique and stable per order, e.g. purchase_<order_id>. Retries with the same ID won't be double-counted.
  5. Turn on the domain allowlist for the pixel Events Manager > Toco's Pixel > Settings > Traffic permissions: add toco.id (and official subdomains) to the allowlist, so data from other domains such as ngrok isn't counted.

Builder pseudocode

// Called when checkout is created (InitiateCheckout) and when payment succeeds (Purchase)
function buildMetaEvent(eventName, order, ctx) {
  const items = order.items.map(i => ({ id: i.listing_id, quantity: i.qty, item_price: i.price }));

  const event = {
    event_name: eventName,                         // "InitiateCheckout" | "Purchase"
    event_time: toUnixSeconds(eventName === "Purchase" ? order.paid_at : order.created_at),
    event_id:   `${eventName.toLowerCase()}_${order.id}`,
    user_data: {
      external_id: [sha256(normalize(order.user_id))],
      em: order.email ? [sha256(normalize(order.email))] : undefined,
      ph: order.phone ? [sha256(normalizePhone(order.phone))] : undefined,
      client_ip_address: ctx.client_ip,          // shopper's IP, not the server's
      client_user_agent: ctx.user_agent
    },
    custom_data: {
      currency: "IDR",
      value: order.items_total,
      content_type: "product",
      content_ids: items.map(i => i.id),          // listings.id UUID
      contents: items,
      num_items: items.reduce((n, i) => n + i.quantity, 0),
      order_id: order.id
    }
  };

  if (ctx.platform === "web") {
    event.action_source = "website";
    event.event_source_url = ctx.page_url || "https://toco.id/checkout";
    event.user_data.fbp = ctx.fbp;
    event.user_data.fbc = ctx.fbc;
  } else {                                       // app_android | app_ios
    event.action_source = "app";
    event.user_data.anon_id = ctx.anon_id;
    if (ctx.tracking_enabled && ctx.madid) event.user_data.madid = ctx.madid;
    event.app_data = {
      advertiser_tracking_enabled: ctx.tracking_enabled ? 1 : 0,
      application_tracking_enabled: 1,
      extinfo: buildExtinfo(ctx)                 // 16 elements, Meta's official format
    };
  }
  return event;
}

Testing and verification

While testing, add the test_event_code parameter (from the Test events tab in Events Manager) to Conversions API requests, so test events show up separately and don't mix with real data.

FAQ

Checkout and Purchase are only sent from the backend. Is that a problem?

No. Server-only events through the Conversions API are a supported and common setup. There's no need to add Checkout or Purchase events on the front end. Only the action_source label and the completeness of shopper data need fixing.

Why not label every order "website", since it's sent from the server?

action_source says where the conversion happened, not which system sent the event. An order created in the app must be labelled "app", even when the server sends it. If it stays "website", Meta can't pair it with app AddToCart and the Collaboration Center issue won't go away.

What if an iOS user declines tracking (ATT)?

Still send the event. Set advertiser_tracking_enabled = 0 and don't send madid. Keep sending anon_id, external_id, em and ph.

One order has products from several stores. What then?

Put every listings.id in content_ids and contents, with value = the total value of all items in that order. If the system splits one checkout into several orders per store, send one Purchase per order, each with its own event_id.

Does AddToCart need to change?

No, unless the checks show its content_ids aren't listing UUIDs, or the "Buy now" flow doesn't send AddToCart.

After the fix, will the catalog match rate go above 90%?

Probably not, and that's expected. The catalog only holds Official Store products, while most orders come from non-official stores. The catalog match rate isn't one of the requirements being addressed here.
