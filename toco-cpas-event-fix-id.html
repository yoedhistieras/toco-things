Perbaikan data pembelian Toco ke Meta, supaya CPAS bisa aktif

Halaman ini punya dua bagian. Bagian A menjelaskan masalahnya dengan bahasa sehari-hari. Bagian B adalah spesifikasi lengkap untuk tim developer.

Bagian A

Penjelasan tanpa istilah teknis

Untuk tim marketing, manajemen, dan siapa saja yang perlu paham masalahnya tanpa harus membaca kode.

Ringkasnya

TujuannyaMengaktifkan CPAS di Collaboration Center, supaya brand atau seller bisa beriklan memakai katalog Toco tanpa harus dibuatkan katalog satu per satu.

Yang menghalangiMeta menolak data pembelian Toco. Menurut Meta, ada pembelian yang "tidak pernah masuk keranjang".

PenyebabnyaPembelian dari aplikasi Toco dilaporkan ke Meta seolah-olah terjadi di website.

PerbaikannyaSatu bagian di sistem backend Toco, yaitu bagian yang melaporkan pembelian ke Meta. Bagian lain tidak perlu diubah.

Apa yang sebenarnya terjadi

Bayangkan Meta sebagai pemeriksa yang mencocokkan dua catatan: siapa yang memasukkan barang ke keranjang, dan siapa yang akhirnya membayar. Kalau dua catatan itu tidak nyambung, Meta menganggap datanya tidak bisa dipercaya.

Langkah 1

Masuk keranjang

Pembeli di aplikasi menekan "tambah ke keranjang". Aplikasi melapor ke Meta: "ada yang masukin keranjang, dari aplikasi." Ini sudah benar.

Langkah 2

Bayar

Pembeli yang sama membayar. Server Toco melapor ke Meta: "ada yang bayar, dari website." Ini yang salah, karena pembeliannya terjadi di aplikasi.

Hasilnya

Meta bingung

Di aplikasi ada ±7.000 orang masukin keranjang per hari tapi tidak ada yang bayar. Di website, hampir semua yang masukin keranjang langsung bayar. Dua-duanya tidak masuk akal.

Yang perlu diluruskanMelaporkan pembayaran lewat server (bukan dari tampilan website atau aplikasi) itu tidak masalah dan memang cara yang umum. Yang salah hanya label asalnya: pembelian dari aplikasi harus dilabeli "aplikasi".

Sekarang vs setelah diperbaiki

Sekarang

Belanja di aplikasi→dicatat "website"
Belanja di website→dicatat "website"

Semua pembelian menumpuk di "website". Meta tidak bisa mencocokkan dengan aktivitas keranjang di aplikasi, jadi CPAS ditolak.

Setelah diperbaiki

Belanja di aplikasi→dicatat "aplikasi"
Belanja di website→dicatat "website"

Setiap pembelian tersambung ke aktivitas keranjang di tempat yang sama. Meta bisa memverifikasi datanya dan CPAS bisa diaktifkan.

Yang kita minta ke developer

Tidak perlu diubah

  • Laporan "masuk keranjang" dari aplikasi dan website
  • Cara Toco melaporkan checkout dan pembayaran lewat server
  • Tidak perlu menambah pelacakan di tampilan website atau aplikasi

Perlu diubah

  • Bagian server yang melaporkan checkout dan pembayaran ke Meta
  • Pengaturan pixel: batasi hanya untuk domain toco.id

Empat hal yang harus dilakukan, dalam bahasa sederhana

  1. Server harus tahu setiap pesanan datang dari aplikasi atau website.Saat ini sistem pesanan tidak mencatat hal ini, jadi semuanya dianggap website.
  2. Pesanan dari aplikasi dilaporkan sebagai "aplikasi", lengkap dengan identitas perangkatnya.Identitas perangkat ini yang dipakai Meta untuk menyambungkan pembayaran dengan aktivitas keranjang di aplikasi.
  3. Pesanan dari website dilaporkan lengkap dengan alamat halaman dan data browser pembeli.Saat ini 95% laporan tidak menyertakan alamat halaman, sehingga Meta sulit menyambungkannya ke klik iklan.
  4. Pakai alamat internet (IP) pembeli, bukan alamat server Toco.Sekarang banyak laporan terlihat datang dari "orang yang sama" karena semuanya memakai alamat server.

Setelah developer selesai

Hasilnya bisa dicek di hari yang sama lewat fitur tes di Meta. Status di Collaboration Center biasanya baru berubah beberapa hari kemudian, karena Meta menilai dari data beberapa hari terakhir. Setelah statusnya hijau, tim marketing tinggal klik Finish untuk mengaktifkan CPAS.

AddToCart dari app dan web sudah berada di jalur yang benar. Yang perlu diubah hanya sender Purchase dan InitiateCheckout di backend.

Cek sebelum coding

Jawaban poin-poin ini menentukan detail implementasi. Centang tersimpan di browser masing-masing.

Langkah implementasi

Prinsipnya: data pembeli ditangkap saat request checkout masuk (selagi request dari device atau browser masih ada), disimpan bersama order, lalu dipakai saat event dikirim. Purchase biasanya dikirim setelah pembayaran sukses, saat request dari pembeli sudah lewat.

  1. Simpan konteks tracking saat checkout dibuat Tambahkan kolom di orders atau tabel baru (misalnya order_tracking_context, satu baris per order):
    • platform: app_android, app_ios, atau web
    • client_ip dan user_agent dari request checkout
    • Web: fbp, fbc (dari cookie), page_url
    • App: anon_id, madid (advertiser ID, kosongkan kalau user tidak mengizinkan), tracking_enabled (status izin tracking), dan data perangkat untuk extinfo
  2. App mengirim identifier perangkat ke API checkout Backend tidak bisa tahu identitas device sendiri, jadi app perlu menyertakannya di request checkout (header atau body):
    • anon_id dari Facebook SDK (Android: AppEventsLogger.getAnonymousAppDeviceGUID(context), iOS: AppEvents.shared.anonymousID)
    • Advertiser ID (GAID / IDFA) kalau user mengizinkan, beserta status izinnya (iOS: hasil ATT)
    • Versi app, versi OS, model device, locale, timezone untuk extinfo
  3. Cabangkan builder event berdasarkan platform Sender Purchase dan InitiateCheckout membaca konteks dari langkah 1, lalu membentuk payload app atau web. Lihat pseudocode di bawah dan tabel spesifikasi field.
  4. Atur waktu dan ID event
    • InitiateCheckout dikirim saat checkout dibuat. Purchase dikirim saat pembayaran sukses.
    • event_time = waktu kejadian sebenarnya (unix detik), bukan waktu kirim. Meta menerima event sampai 7 hari ke belakang.
    • event_id unik dan stabil per order, misalnya purchase_<order_id>. Retry dengan ID yang sama tidak akan dihitung dobel.
  5. Aktifkan allowlist domain di pixel Events Manager > Toco's Pixel > Settings > Traffic permissions: tambahkan toco.id (dan subdomain resmi) ke allowlist, supaya data dari domain lain seperti ngrok tidak dihitung.

Pseudocode builder

// Dipanggil saat checkout dibuat (InitiateCheckout) dan saat pembayaran sukses (Purchase)
function buildMetaEvent(eventName, order, ctx) {
  const items = order.items.map(i => ({ id: i.listing_id, quantity: i.qty, item_price: i.price }));

  const event = {
    event_name: eventName,                         // "InitiateCheckout" | "Purchase"
    event_time: toUnixSeconds(eventName === "Purchase" ? order.paid_at : order.created_at),
    event_id:   `${eventName.toLowerCase()}_${order.id}`,
    user_data: {
      external_id: [sha256(normalize(order.user_id))],
      em: order.email ? [sha256(normalize(order.email))] : undefined,
      ph: order.phone ? [sha256(normalizePhone(order.phone))] : undefined,
      client_ip_address: ctx.client_ip,          // IP pembeli, bukan IP server
      client_user_agent: ctx.user_agent
    },
    custom_data: {
      currency: "IDR",
      value: order.items_total,
      content_type: "product",
      content_ids: items.map(i => i.id),          // UUID listings.id
      contents: items,
      num_items: items.reduce((n, i) => n + i.quantity, 0),
      order_id: order.id
    }
  };

  if (ctx.platform === "web") {
    event.action_source = "website";
    event.event_source_url = ctx.page_url || "https://toco.id/checkout";
    event.user_data.fbp = ctx.fbp;
    event.user_data.fbc = ctx.fbc;
  } else {                                       // app_android | app_ios
    event.action_source = "app";
    event.user_data.anon_id = ctx.anon_id;
    if (ctx.tracking_enabled && ctx.madid) event.user_data.madid = ctx.madid;
    event.app_data = {
      advertiser_tracking_enabled: ctx.tracking_enabled ? 1 : 0,
      application_tracking_enabled: 1,
      extinfo: buildExtinfo(ctx)                 // 16 elemen, format resmi Meta
    };
  }
  return event;
}

Cara tes dan verifikasi

Saat tes, tambahkan parameter test_event_code (diambil dari tab Test events di Events Manager) di request ke Conversions API, supaya event uji muncul terpisah dan tidak tercampur data asli.

Pertanyaan umum

Checkout dan Purchase hanya dari backend. Apakah itu masalah?

Tidak. Event server-only lewat Conversions API adalah setup yang didukung dan umum. Tidak perlu menambah event Checkout atau Purchase di front end. Yang perlu diperbaiki hanya label action_source dan kelengkapan data pembeli.

Kenapa tidak semua order dilabeli "website" saja, karena dikirim dari server?

action_source menunjukkan tempat konversi terjadi, bukan sistem yang mengirim event. Order yang dibuat di app harus berlabel "app", meskipun dikirim dari server. Kalau tetap "website", Meta tidak bisa memasangkannya dengan AddToCart app dan issue di Collaboration Center tidak akan hilang.

Bagaimana kalau user iOS menolak izin tracking (ATT)?

Event tetap dikirim. Isi advertiser_tracking_enabled = 0 dan jangan kirim madid. anon_id, external_id, em dan ph tetap dikirim.

Satu order berisi produk dari beberapa toko. Bagaimana?

Masukkan semua listings.id ke content_ids dan contents, dengan value = total nilai semua barang di order itu. Kalau sistem memecah satu checkout jadi beberapa order per toko, kirim satu Purchase per order dengan event_id masing-masing.

Apakah AddToCart perlu diubah?

Tidak, kecuali hasil cek menunjukkan content_ids-nya bukan UUID listing, atau alur "Beli Sekarang" tidak mengirim AddToCart.

Setelah fix, apakah match rate katalog akan di atas 90%?

Kemungkinan tidak, dan itu wajar. Katalog hanya berisi produk Official Store, sedangkan sebagian besar order datang dari toko non-official. Match rate katalog tidak termasuk syarat yang sedang dikejar di sini.
